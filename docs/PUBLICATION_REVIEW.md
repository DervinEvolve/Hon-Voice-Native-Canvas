# Canvas publication review

This is a source-publication candidate for the `infinite-scene-agents` canvas. The existing repository remains private and the PR is draft. A passing build does not authorize production promotion or make the historical repository safe to expose.

## Implemented boundaries

- All 158 default Node API entrypoints require provider-verified Supabase or pinned Privy identity and an explicit allowed-user list. Missing configuration denies access. The routing proxy is an additional check. The legacy rewrite bypass discovered in a private preview is removed.
- Mutation and read requests claim separate atomic hourly database slots per verified user. The defaults are 60 writes and 600 reads. Exhaustion returns 429; an unavailable ledger denies dispatch. These caps do not replace provider dollar budgets.
- Google/Notion starts use authenticated POSTs. Callbacks require signed, expiring state and explicit redirect URLs. Provider cookies are signed, subject-bound and HttpOnly; production uses host-only Secure cookies. Cookies are signed, not encrypted. Existing unsigned connections must reconnect. Internal calls forward proof only to an operator/platform configured origin. Veo keeps authenticated polling without the old no-op callback.
- SHARP jobs have owner-scoped IDs, private storage and expiring result URLs. New scenes save the job ID and refresh owner-checked URLs when opened. The Modal worker requires dedicated proxy proof, exact source hosts and bounded input/output. LOD subprocesses use argument arrays without a shell; public multi-file LOD output requires an explicit switch.
- Canvas-history migration removes wallet-string authorization, uses verified database identity and caller privileges, pins search paths and revokes old RPC overloads. History is owner-private; a Privy UI identity or wallet alone is not a Supabase database session. Legacy unowned rows stay inaccessible.
- Download/upload/export paths use approved HTTPS hosts, no redirects and bounded reads. Cloudinary uploads do not accept server-local paths. Export names cannot traverse directories; at most eight assets are accepted, at 32 MiB each.
- Generated game frames have opaque origins and constrained parent messages. Development servers bind to loopback.

## Deployment and execution limits

Source publication is different from opening an unrestricted generation service. Rollout requires the protected API, database migrations, worker configuration and client to be coordinated. Real sign-in/speech/tool/export/storage/rendering checks and provider spending controls remain operator tasks before exposing a deployment. An existing placeholder domain is not evidence of the canvas's deployment status.

The voice scene builder executes model-generated PlayCanvas/behavior code in the application context, with the signed-in session and the access token the page attaches to `/api` calls. It is not sandboxed: content the voice model reads (Notion pages, memories, image descriptions) can steer that code. It is off by default: the browser runs it only in a build with `VITE_ENABLE_SCENE_CODE_EXECUTION=true`, and the server generates it only with `HON_ENABLE_SCENE_CODE_EXECUTION=true`. Turn both on only for a private, trusted workspace. This is a trusted-author programming experiment, not a sandbox for untrusted shared scenes or code; moving it into an opaque-origin frame is still work in progress. The opaque game-frame check does not establish isolation for that separate execution path. Do not grant untrusted people access to an operator's signed-in workspace. Broader multi-user isolation remains unfinished.

The reviewed SHARP service accepts an image. The complete video/frame-to-splat pipeline has not yet been traced or extracted. No claim of independent model training is made.

Final source inspection found a hard-coded upload-key fallback and a browser voice client expecting a provider key. The fallback is removed; Pika uploads and ElevenLabs speech now use protected first-party APIs. An input/response/error regression covers the actual speech handler. Unused duplicate legacy API/application copies, generated exports/patches and the unused PR-target label workflow are excluded from the publication tip; private backups retain them. The source scanner missed the short upload-key value, so zero scanner matches alone is not claimed as clearance. The old ImgBB key also needs retirement before treating historical copies as harmless.
